## 5 Why a trailing newline breaks EVALSHA

The server hashes the exact bytes it receives in `SCRIPT LOAD` and keys the script cache by that sha1.  A client that sends the body plus one newline sends 72 bytes, not 71, and the server computes a different sha1 for it.  The Wasm artifact and the shell artifact then hold two different keys for what a reader sees as the same script, LUA-SAME fails because the two sha256 values differ, and one of the two artifacts gets NOSCRIPT on every EVALSHA until it falls back to EVAL (R-Q5), which defeats LOAD-ONCE (R-M0-5).  A heredoc always ends its last line with a newline before the delimiter, so a body that carried a trailing newline in the file could never round-trip through the R-M0-6 form:  the substitution strips every trailing newline, and the bytes would differ from the file.  The rule of section 6 removes the ambiguity at the source.

## 6 Decision S0-D5, the canonical body rule

A canonical Lua body is a byte sequence with these four properties:

1. Line separator LF (0x0a) only.
2. No CR (0x0d) anywhere.
3. No BOM;  the first byte is the first byte of the source text.
4. No trailing newline;  the last byte is the last byte of the last source line.

Both artifacts carry the canonical bytes:  prog.wasm as the module data and prog.sh as the quoted heredoc of section 2.  LUA-SAME compares the sha256 of the bytes extracted by running the assignment against the sha256 of the module bytes, and the EVALSHA key is the sha1 of the same bytes.  The Int64 spine fixture value past 2^53 is 9007199254740993, carried as a bulk string on both boundaries (R-X2, R-M0-7);  spike (g) records the boundary probes.

Evidence for the rule: the BODY-SAME line of section 3, the 0x29 last byte of section 4, and the BODY-DIFF line of section 5.
